# MES 设备建模设计（通用版）

> 状态：草稿 v1（2026-07-20）
> 性质：纯理论探讨 / 通用 MES 设备建模框架，不绑定 bmos 现有实现
> 关联：本仓库 `docs/code-wiki/entities/_platform/MES设备建模概要（精炼版）.md` 是本文的思考起点

---

## 0. 摘要

本设计提出一套以 **"位置漏斗 + 粗粒度能力匹配"** 为核心的 MES 设备模型，目标是用**可预测、可实现**的方式，让同一套工艺能适配多产线、多房间的现场配置。

核心取舍：

- **不追求能力级参数精筛**（两台都能离心的设备不再按转速区分），换取匹配的确定性和实现简单度。
- **用位置逐级具化替代能力匹配承担"灵活性"**：工艺绑多产线、工序绑多房间，执行时收敛到具体房间，房间内再做能力资格筛选。

最终设备分配逻辑：

```
选定产线 ∩ 工序允许的房间 ∩ 房间内具备所需能力的设备 ∩ 状态可分配 → 选一台
```

设备控制与采集（§12）作为正交维度引入：MES 通过命令执行器 + 协议驱动的分层抽象直接控制设备和采集数据，协议可配置，直连为主、Batch 预留。

设备程序层（§13，Batch 抽象）在工艺与设备点位之间引入"程序"封装：工艺只声明执行什么程序，程序执行器按设备 executeMode 统一路由到直连展开或现场控制层下发；监控、断电恢复、GMP 审计的工程责任收敛到此层。

数据采集存储（§14）将采集数据作为时序数据独立于业务数据存储，按热/温/冷三层分层管理，写入时带业务上下文 tag 以支撑批记录回放与 GMP 追溯。

## 1. 设计目标

建立**可管理、可调度、可控制、可扩展**的设备模型，而非仅是设备台账。具体目标：

1. **工艺与设备解耦**：工艺定义不写死具体设备，同一套工艺能在不同产线、不同房间执行。
2. **可预测**：工艺工程师和现场操作员能大致知道会用到哪类设备，排程、追溯、调试可读。
3. **可落地**：匹配逻辑能用确定性的查询表达，不依赖复杂匹配引擎。
4. **可演进**：设备改装、加装、换型不应大规模改动主数据。

### 非目标（明确不做）

- **不做能力参数级精筛**：不在转速/量程/精度层面区分同能力设备。
- **不做运行时智能调度**：负载均衡、就近、优先级等策略由调度器决定，本设计只提供候选集。
- **不做物流路径可达性计算**：位置约束止于"房间可达"，跨房间搬运交给物流/AGV/WMS。

## 2. 核心决策链

经过设计讨论，确定以下五项选型，构成整套建模的基础：

| # | 决策点 | 结论 | 关键理由 |
|---|---|---|---|
| 1 | 解耦程度 | 粗粒度能力匹配 | 强解耦不可预测；纯弱解耦会跨产线串设备（被位置漏斗消解） |
| 2 | 能力匹配粒度 | 布尔资格（能/不能） | 不做参数精筛，避免匹配不确定性 |
| 3 | 位置模型 | 4 级漏斗：工艺→产线→房间→设备 | 工位=物理位置，不参与匹配 |
| 4 | 能力来源 | 类型默认 + 实例可增删 | 兼顾登记便利与改装灵活 |
| 5 | 状态职责 | 三层正交（连接/运行/健康）+ 占用标志，派生 allocatable | 服务控制+运维+分配；业务状态归工序 |

## 3. 位置模型：逐级具化路径

位置不是一个"筛子"，而是一条**逐级具化**的路径：每一层的选择都把候选集收紧一次。

### 3.1 层级与绑定关系

```
工艺 (Process)        绑定 多条产线（抽象，工艺可跨产线复用）
 │
 ▼  排程期：选定一条产线
 │
产线 (Line)
 │
 ▼  工序绑多房间，执行时按选定产线选房间
 │  候选房间 = 该工序允许的房间 ∩ 该产线下辖的房间
 │
房间 (Room)
 │
 ▼  房间→设备这一跳直接跨过工位
 │
工位 (Station)        物理位置，不参与工艺匹配（透明）
 │
 ▼  设备分配期：在房间内按能力+状态筛
 │
设备 (Equipment)
```

### 3.2 每一层的候选集

| 层级 | 动作 | 选择时机 | 候选集 |
|---|---|---|---|
| 工艺 | 绑多产线 | 设计期 | 全平台 |
| 产线 | 选定一条 | 排程期 | 该产线可达 |
| 房间 | 工序允许房间 ∩ 产线房间 | 排程/执行前 | 一个房间 |
| 工位 | （透明） | — | — |
| 设备 | 房间内 ∩ 能力 ∩ 状态 | 执行时 | 一台 |

### 3.3 关键约束

- **工艺绑产线、工序绑房间**：工艺层做"产线无关"抽象，工序层做"房间无关"抽象（一个工序可在多个房间执行）。
- **工位是物理坐标，且对匹配"透明"**：工位承载设备的物理归属（可视化、点检、定位用），**不参与工艺匹配**。工艺眼里只有"房间 + 能力需求"。
  - **"透明"的含义**：此处借用计算机领域用法——"对匹配逻辑不可见、感觉不到工位存在"，而非"看得清楚"。即分配查询里没有工位字段，匹配在房间层就收口。
  - **透明 ≠ 不存在**：工位仅对**匹配环节**隐身；在台账登记（stationId）、现场定位、赋码（工位码含上溯）等场景仍完全可见。
  - **目的**：让物理布局变化（设备挪位、备用顶替）不冲击工艺主数据。
- **房间是匹配的物理边界**：候选集一旦收敛到某个房间，不再跨房间。跨房间搬运属于物流问题，不属于设备分配问题。

## 4. 能力模型：粗粒度资格筛

### 4.1 能力是什么

**能力是设备"能干哪类活"的布尔标签**，例如：`可离心`、`可称量`、`可容器`、`可打印`、`可CIP`、`可SIP`。

- 能力**不带参数范围**（不写"转速 3000–5000rpm"）。
- 两台同具"可离心"能力的设备，**视为等价**，匹配时不区分。

### 4.2 能力的来源（设计③：类型默认 + 实例可增删）

设备的**有效能力集**由三部分计算：

```
设备有效能力集 = 类型默认能力 ∪ 实例新增能力 − 实例移除能力
```

| 来源 | 说明 | 典型场景 |
|---|---|---|
| 类型默认能力 | 设备选定类型后自动继承 | 标准设备，登记时选类型即可 |
| 实例新增能力 | 设备实例上显式增加 | 改装、加装模块后具备新能力 |
| 实例移除能力 | 设备实例上显式移除 | 某模块故障停用、或临时降级 |

这样兼顾了两种诉求：

- **登记便利**：90% 的标准设备只需选类型，能力自动带出。
- **改装灵活**：少数改装设备通过增删能力表达差异，不必新建类型。

### 4.3 能力匹配规则

工艺工序声明 `所需能力清单`，设备暴露 `有效能力集`，匹配就是子集判定：

```
match(step, equipment) =
    step.requiredCapabilities ⊆ equipment.effectiveCapabilities
```

**只有"能/不能"两种结果**，不存在"部分匹配"或"按参数排序"。

### 4.4 能力 vs 类型 vs 分类（三者职责）

这三者最容易混淆，明确各自职责：

| 维度 | 职责 | 是否参与匹配 | 形态 |
|---|---|---|---|
| **分类 (Category)** | 统计、分组、展示 | ❌ 不参与 | 树形（如"加工设备/检测设备"）|
| **类型 (Type)** | 继承默认能力、规格参数模板 | ✅ 间接（通过默认能力）| 扁平或浅层（如"离心机""电子秤"）|
| **能力 (Capability)** | 匹配的硬筛条件 | ✅ 直接 | 扁平标签集 |

> 类比：**分类**是图书馆的书架分区（找书用），**类型**是书的版次（决定内容），**能力**是书讲什么主题（决定能不能回答你的问题）。

## 5. 设备台账：一台设备登记什么

按用途分层，避免"什么都往设备表塞"。

### 5.1 身份层（Identity）

唯一标识这台设备本身。

| 字段 | 用途 |
|---|---|
| 设备编码 (code) | 全局唯一，赋码见 §6 |
| 名称 | 展示 |
| 型号 | 展示、备件匹配 |
| 厂家 / 制造商 | 展示、维保 |
| 序列号 (SN) | 实物追溯 |
| 资产编号 | 财务对接 |

### 5.2 归属层（Location）

定位这台设备在哪里。

| 字段 | 用途 |
|---|---|
| 所属工位 (stationId) | 物理坐标（房间/产线由此上溯）|
| 工位 → 房间 → 产线 | 通常冗余存储或通过工位上溯 |

### 5.3 分类与类型层（Classification & Type）

| 字段 | 用途 |
|---|---|
| 分类 (categoryId) | 统计/展示 |
| 类型 ( typeId) | 决定默认能力、规格参数模板 |

### 5.4 能力层（Capability）

| 字段 | 用途 |
|---|---|
| 有效能力集 | **匹配用**，由类型默认 ∪ 新增 − 移除计算 |
| 新增能力列表 (addedCapabilities) | 实例级覆盖 |
| 移除能力列表 (removedCapabilities) | 实例级覆盖 |

> 有效能力集可物化存储（每次增删时刷新），或动态计算。匹配高频建议物化。

### 5.5 规格参数层（Properties）

| 字段 | 用途 |
|---|---|
| 量程 / 精度 / 转速 / 容量 / 电压 … | **仅展示和点检**，不参与匹配 |

> 注意：这些参数**不参与匹配**。它们是给人看的（操作员点检、维保核对），不是给匹配引擎用的。刻意不把它们做成匹配条件，是本设计的核心取舍之一。

### 5.6 连接与采集层（Connection & Acquisition）

本层的完整结构（ControlProfile / AcquisitionProfile、配置组织、覆盖约束）见 §12.9 与 §12.10。此处仅说明其在台账中的归属：

| 维度 | 用途 | 详见 |
|---|---|---|
| 控制配置 ControlProfile | 控制接口对接（协议、endpoint、命令映射）| §12.9 / §12.10 |
| 采集配置 AcquisitionProfile | 数据采集（采集点、周期、报警规则）| §12.9 / §12.10 |

### 5.7 状态层（Runtime State）

见 §7。本层承载设备的当前三层状态（连接/运行/健康）+ 占用标志；状态变更历史与日志见 §7.6。

### 5.8 登记分层速查

| 层 | 匹配相关？ | 备注 |
|---|---|---|
| 身份 | 否 | 标识 |
| 归属 | ✅ 是（位置筛子）| 通过工位上溯 |
| 分类 | 否 | 统计展示 |
| 类型 | ✅ 间接（带出默认能力）| 决定能力基线 |
| 能力 | ✅ 是（硬筛）| 匹配核心 |
| 规格参数 | 否 | 仅展示 |
| 连接/采集 | 否 | 控制与数采 |
| 状态 | ✅ 是（可用筛子）| 见 §7 |

## 6. 赋码体系

赋码要支撑两类反查：**按位置反查**（这条产线/这个房间有哪些设备）、**按能力反查**（哪些设备具备某能力）。

### 6.1 编码对象

| 对象 | 编码示例 | 用途 |
|---|---|---|
| 产线 | `LINE-01` | 位置反查 |
| 房间 | `LINE-01-RM-003` | 位置反查（含上溯）|
| 工位 | `LINE-01-RM-003-ST-02` | 物理坐标（含上溯）|
| 设备 | `EQP-2026-0001` | 全局唯一 |
| 类型 | `TYPE-CENTRIFUGE` | 能力继承锚点 |
| 能力 | `CAP-CENTRIFUGE` | 匹配键 |

### 6.2 编码原则

- **位置编码含上溯**：工位码内嵌产线/房间段，便于一眼定位，也便于按前缀反查（`LIKE 'LINE-01-RM-003-%'` 查该房间所有工位/设备）。
- **设备码独立**：设备可能挪位置，故设备码不内嵌位置（挪位置不改码）。
- **能力码全局稳定**：能力是工艺匹配的键，一经发布不改名（改用版本/废弃机制）。
- **类型码稳定**：类型码改动会影响所有该类型实例的默认能力继承，需走变更流程。

### 6.3 反查模式

```
按位置反查： WHERE stationId LIKE 'LINE-01-RM-003-%'           → 该房间所有设备
按能力反查： WHERE 'CAP-CENTRIFUGE' = ANY(effectiveCapabilities) → 全平台具备该能力的设备
按产线反查： WHERE stationId LIKE 'LINE-01-%'                   → 该产线所有设备
组合反查：   WHERE stationId LIKE 'LINE-01-RM-003-%'
             AND 'CAP-CENTRIFUGE' = ANY(effectiveCapabilities)
             AND status = AVAILABLE                              → 设备分配的候选集
```

> 注：此处 `status = AVAILABLE` 为表述简洁所用的派生判定；实际过滤条件见 §7.3 的 `allocatable`（Connection=Online ∧ Operation∈{Idle,Running,Pause} ∧ Health=Normal ∧ 未占用）。

## 7. 状态建模

设备状态**不混成一个 status 字段**。MES 真正控制设备时，状态至少分三层，各自由不同来源维护、独立变化：

```
设备状态 = 连接态 × 运行态 × 健康态   （正交，不是单一字段）
另加：占用标志（业务行为，与三层正交）
```

> 为何不混成一个字段：连接、运行、健康是**独立变化**的维度。一台设备可能 Online 但 Alarm，也可能 Offline 但健康。压成一个字段会丢失信息，排障、运维、操作员看板都无法回答"这台设备为什么不能用"。

> 为何**不设**"业务状态"层：待料、等待人工、等待 AGV、等待放行等，本质是**工序执行状态**，绑定工序实例，不属于设备本体。同一台设备被不同工序占用时，这些状态会不同——说明它的归属是工序，不是设备。故业务状态归工序执行引擎管理，设备不承载。

### 7.1 三层正交状态

| 层级 | 取值 | 来源 | 说明 |
|---|---|---|---|
| **连接态** Connection | Offline / Connecting / Online | 协议驱动（§12.2）| 通信层探活。`Connecting` 避免把"正在连"误判为离线 |
| **运行态** Operation | Idle / Running / Pause / Stopping / Error | 设备点位上报 | 设备自身在干什么。`Error` 指设备自报的运行异常（过载、超温），瞬时、可能自恢复 |
| **健康态** Health | Normal / Alarm / Repair / Maintenance / Disabled | 维保流程 + 报警规则 | 设备长期可用性。`Alarm` 持续需人工介入；`Repair`=故障维修；`Maintenance`=预防性保养；`Disabled`=人为停用 |

> 运行态 `Error`（瞬时、可能自恢复）与健康态 `Alarm`（持续、需人工介入）刻意分开：一个设备可能短暂 Error 但健康仍 Normal；也可能健康 Alarm 但运行已自行恢复。

### 7.2 占用标志（与三层正交）

占用是**业务行为**（某工序占用了这台设备），不是设备本体状态，故单独表达：

| 字段 | 取值 | 来源 |
|---|---|---|
| occupied | true / false | 工序执行引擎 apply/release |
| occupant | 工序实例/批次 ID | 占用方标识 |
| heartbeatTimestamp | 心跳时间戳 | 见 §7.4 |

占用与三层状态正交——一台 Online + Idle + Normal 的设备，可能已占用、也可能未占用。

### 7.3 分配判定：派生属性 allocatable

分配场景需要"能不能分给工序"的简单答案。由三层状态 + 占用标志**派生**，不独立存储：

```
allocatable =
       Connection == Online
   AND Operation IN (Idle, Running, Pause)      // Error 不可分配
   AND Health == Normal                           // Alarm/Repair/Maintenance/Disabled 不可分配
   AND NOT occupied                               // 未被占用
```

- **分配候选集**过滤条件即 `allocatable = true`。
- `allocatable` 是**实时派生**，不落库——避免与三层状态冗余、不一致。

### 7.4 占用心跳机制（防丢设备）

占用期间必须周期续命，否则自动释放：

1. **占用 (apply)**：`occupied=true`，记录占用方，写心跳时间戳。
2. **心跳续命 (heartbeat)**：占用方周期调用，刷新时间戳。
3. **超时释放**：定时任务扫描，心跳超时的占用自动释放（changeType=BUSINESS），避免业务进程崩溃导致设备永远占用。

> 心跳周期和超时阈值是关键参数（典型：心跳 30s，超时 2min）。
> 此心跳是**业务级**，与 §12.7 的**通信级心跳**区分：前者防业务丢设备，后者探通信连接存活。

### 7.5 各层状态机（独立）

三层状态各自有自己的流转，互不约束（除派生判定外）：

**连接态**：
```
Offline ──connect()──► Connecting ──成功──► Online
   ▲                                         │
   └────────────断线─────────────────────────┘
                       Connecting ─失败/超时─► Offline
```

**运行态**（由设备点位上报驱动，MES 观测）：
```
Idle ──启动──► Running ──暂停──► Pause ──恢复──► Running
  ▲              │                 │
  │              │停止/完成         │停止
  │              ▼                 ▼
  └────────── Stopping ◄──────────┘
  │
  └─任意态──异常──► Error ──自恢复/复位──► Idle
```

**健康态**：
```
Normal ──报警──► Alarm ──转维修──► Repair ──修好──► Normal
  │                 │
  │                 └──转为保养──► Maintenance ──完成──► Normal
  │
  └──人为停用──► Disabled ──启用──► Normal
```

### 7.6 状态变更日志

三层状态的所有变更分别落日志，含变更类型：

| changeType | 含义 |
|---|---|
| MANUAL | 手动操作（apply/release/启用/停用）|
| BUSINESS | 业务流转（心跳超时自动释放）|
| EVENT | 设备点位上报（运行态变化）|
| SYSTEM | 系统探活（连接态变化）|
| EXPIRE | 效期到期（校验证书过期触发健康态 Alarm）|

日志字段：设备、状态层级（Connection/Operation/Health/Occupancy）、pre_value、post_value、changeType、操作人/来源、时间、关联批次/工序。

### 7.7 设计权衡记录

| 决策 | 选择 | 放弃了什么 | 何时重新考虑 |
|---|---|---|---|
| 状态分层 | 三层正交 + 占用标志 | 单字段的查询简单 | 永不——分层在控制+运维场景下是必需的 |
| 业务状态 | 不设（归工序）| 操作员在设备上看"在等什么" | 当设备看板确需聚合显示工序状态时，做派生视图而非设备字段 |
| 分配判定 | 派生 allocatable，不存储 | 少一次派生计算 | 永不——存储会引入一致性维护负担 |
| 运行 Error vs 健康 Alarm | 分开 | 一个统一"故障"的简单 | 当现场设备确实无法区分瞬时/持续异常时，合并为 Alarm |
| 状态获取 | 分层差异获取（探活/订阅/轮询/业务登记），Offline 靠 allocatable 兜底 | 一律轮询的简单 | 当现场设备全部支持事件订阅时，可全面切换订阅 |
| Offline 运行态 | 标记陈旧，不编造、不分配 | 自动归零的简单 | 永不——编造状态会误导排障 |

### 7.8 状态的获取与可信度

三层状态由不同机制获取，**可信度不同，且受连接态约束**。落地时必须区分对待，不能一律轮询。

#### 7.8.1 各层状态的获取机制

| 状态层 | 获取方式 | 是否依赖实时连接 | 谁维护 |
|---|---|---|---|
| 连接态 | **探活的副产品**——发命令/读点位的成功失败即判定；驱动周期心跳探活 | 是（周期探活）| 协议驱动（自动）|
| 运行态 | **设备上报**：订阅优先（OPC UA Subscription / MQTT publish），不支持则轮询读运行点位；无通信设备无法获取 | 是（订阅或轮询）| 设备点位上报，MES 观测 |
| 健康态 | **业务态**：Alarm 由报警规则（基于采集数据离线计算）触发；Repair/Maintenance/Disabled 由维保流程登记 | 否 | 维保流程 + 报警规则 |
| 占用标志 | 业务行为，apply/release 时直接写 | 否 | 工序执行引擎 |

> 连接态不需要"专门确认"——它是通信本身的副产品。运行态是最依赖实时连接的一层。健康态基本不依赖连接，是 MES 内部维护的业务状态，断网也不丢。

#### 7.8.2 设备通信能力决定运行态的获取方式

不同设备支持的能力不同，运行态获取方式随之分化，是落地时最大的现实变量：

| 设备通信能力 | 运行态获取方式 | 代价 |
|---|---|---|
| 支持 OPC UA Subscription / MQTT 等事件机制 | 订阅（事件驱动，状态变化自动推）| 保持长连接，开销轻、实时 |
| 只支持读（老旧 PLC / Modbus）| 周期轮询读运行点位 | 间歇连接，开销随设备数线性增长、有轮询延迟 |
| 无通信能力（纯开关设备）| **无法获取**——MES 只能依据"发过 Start"盲猜 | 不可信 |

> 因此设备类型配置（§12.10）应声明其运行态获取能力（订阅 / 轮询 / 无），供运行态采集策略选择。无通信设备的运行态应标记为"不可信"，allocatable 判定按 Offline 处理。

#### 7.8.3 Offline 时各层的语义（关键）

断连期间，三层状态的可信度不同，必须明确：

| 连接态 | 运行态 | 健康态 |
|---|---|---|
| Online | ✅ 最新值 | ✅ 最新值 |
| **Offline** | **❌ 陈旧——停留在最后一次成功读取的值** | ✅ 仍可信（业务态，不受连接影响）|

> Offline 时运行态陈旧是无法避免的物理事实：连不上设备，就不可能知道它现在的动作。**不要**编造（如自动设为 Idle）——那是假数据，会误导排障。

#### 7.8.4 安全性靠 allocatable 兜底，不靠"持续硬连"

既然 Offline 时运行态陈旧，如何保证不被误分配？答案在 §7.3 的派生判定：

```
allocatable = Connection==Online ∧ ...
```

**allocatable 第一关就是连接态。** Offline 设备直接出局，无论其（陈旧的）运行态显示什么。因此：

- **不需要为了"状态准确"而强求设备一直在线**——断连是常态，业务安全性由 allocatable 兜底。
- **正确的工程姿势**：承认"连不上时运行态未知"，靠 Offline 出局保证安全，而不是靠"持续硬连"硬撑。

#### 7.8.5 重连后的状态同步

断连恢复（Online 重新建立）后，运行态是陈旧的，必须同步刷新：

1. **连接恢复** → 驱动将连接态置 Online。
2. **立即拉取运行态** → 主动读一次运行点位（订阅模式也补一次读），刷新运行态。
3. **触发健康态再评估** → 检查断连期间是否有未处理的报警升级。
4. **allocatable 重算** → 刷新后的状态重新参与分配判定。

> 同步期间运行态应标记为"刷新中"或临时保留陈旧值并禁止分配，避免用陈旧值参与判定。

#### 7.8.6 采集与状态获取的关系

运行态的获取（订阅/轮询）与 §12.6 的**数据采集**共用协议通道但职责不同：

| 维度 | 运行态获取 | 数据采集 |
|---|---|---|
| 目的 | 维护 allocatable、驱动业务判定 | 记录历史曲线、报警计算 |
| 数据 | 少量关键状态点位 | 大量时序点位 |
| 频率 | 变化时（订阅）或秒级（轮询）| 高频周期 |

两者可复用同一连接，但逻辑上独立配置（运行态点位归运行态管理，采集点位归 AcquisitionProfile）。

## 8. 设备分配流程

把上述决策合成一条完整的分配流程。

### 8.1 触发场景

工序实例准备执行时，需要一台满足条件的设备。触发方通常是工序执行引擎。

### 8.2 分配流程（时序）

```
工序执行引擎                        设备分配服务
     │
     │  1. 请求分配设备
     │     入参：工序实例ID、选定产线
     │  ─────────────────────────►│
     │                             │
     │                  2. 查工序允许的房间集合
     │                  3. 候选房间 = 允许房间 ∩ 产线下辖房间
     │                  4. 查工序所需能力清单
     │                             │
     │                  5. 候选设备 = SELECT * FROM equipment
     │                     WHERE stationId IN (候选房间下的工位)
     │                       AND 所需能力 ⊆ 有效能力集
     │                       AND allocatable = true   ← 见 §7.3 派生条件
     │
     │                  6. 若候选为空 → 返回失败（无可用设备）
     │                  7. 若候选非空 → 按策略选一台
     │                     （负载均衡/优先级/就近，超出本设计范围）
     │
     │                  8. 占用选中设备（apply）
     │                     → occupied=true，写占用方、心跳
     │
     │  9. 返回选中设备ID           │
     │  ◄─────────────────────────│
     │
     │  10. 工序执行期间周期调用 heartbeat
     │  ─────────────────────────►│
     │
     │  11. 工序完成 → release
     │  ─────────────────────────►│ → occupied=false
```

### 8.3 候选集计算（伪 SQL）

```sql
-- 给定：产线 lineId、工序允许房间 allowedRooms[]、所需能力 reqCaps[]
SELECT e.*
FROM equipment e
JOIN station s ON e.station_id = s.id
WHERE s.room_id IN (
    -- 候选房间 = 工序允许 ∩ 产线下辖
    SELECT id FROM room
    WHERE line_id = :lineId AND id IN (:allowedRooms)
)
AND :reqCaps <@ e.effective_capabilities   -- 所需能力是有效能力的子集
AND allocatable(e)                          -- 派生：见 §7.3
```

### 8.4 失败处理

| 失败原因 | 处理 |
|---|---|
| 候选房间为空 | 工序与产线不匹配（工序绑定的房间不在该产线下）→ 数据错误，需修正主数据 |
| 候选设备为空（有房间无能力匹配设备）| 该房间无满足能力的设备 → 提示运维检查房间设备配置 |
| 候选设备为空（有匹配设备但都占用）| 资源争用 → 排队等待，或人工干预 |
| 候选设备为空（有匹配设备但故障/维护）| 设备不可用 → 通知维保 |

### 8.5 释放与故障

- **正常释放**：工序完成 → release → `occupied=false`，清占用字段。
- **设备异常**：占用中设备运行态变 Error 或健康态变 Alarm → 清占用字段、通知占用方（工序执行引擎需处理中断）。是否自动解除占用由策略决定（见 §13 开放问题）。
- **超时释放**：心跳超时 → 自动 release（changeType=BUSINESS）。

## 11. 与 bmos 现有实现的关系（参考性对照）

> 本节为对照说明，不是改造建议。基于对 bmos 代码（platform factory 子模块 + mes process 子域）的核实。

| 本设计概念 | bmos 现有对应 | 差异 |
|---|---|---|
| 设备类型 (Type) | `bp_equipment_tag`（设备类型树）+ `bp_equipment_tag_property`（类型下属性）| bmos 的 tag 概念≈本设计的 Type，属性里混了状态/参数 |
| 分类 (Category) | `bp_equipment_category`（分类树）| 一致 |
| 能力 (Capability) | 无显式概念（通过 tagCode 间接表达）| bmos 用类型码替代能力，未做能力层抽象 |
| 产线 | `LineService` / `bp_factory_line` | 一致 |
| **房间** | `RoomService` / `bp_factory_room`（含占用 `BpFactoryRoomOccupy`、环境属性、状态日志）| **bmos 有完整房间模块**，且 MES 工序已支持绑房间（`ProcedureModelRoom`）。本设计的房间定位与 bmos 高度一致 |
| 工位 | `FactoryStationService` / `bp_equipment_station`（工位绑设备/用户）| bmos 工序可绑房间**或**工位（`ProcedureModelRoomOrStation`，二选一）；本设计统一为**工位透明**，匹配只在房间层收口 |
| 工序绑房间 | MES `ProcedureModelRoom`（工序模型-房间关联）| **bmos 已实现**，与本设计思路一致 |
| 状态机 | 设备 status 1可用/2不可用/3占用/4故障；房间另有占用状态 | bmos 设备单字段；本设计设备三层正交（连接/运行/健康）+ 占用标志，派生 allocatable。bmos 房间已有独立占用，方向接近 |
| 占用心跳 | applyEquipment + applyEquipmentHeart + XXL-JOB 扫描 | 一致 |
| 程序层 (Batch 抽象) | 无显式概念 | bmos 控制偏点位直连，未抽象"程序"封装 |

> **主要差异（修正后）**：
> 1. **能力层抽象缺失**——bmos 用类型码（tagCode）替代能力，未做独立的布尔能力层，工艺无法按能力匹配。
> 2. **工位角色不同**——bmos 工序可绑房间**或**工位（二选一），工位仍可能参与匹配；本设计统一为工位透明，匹配只在房间收口。
> 3. **设备状态分层**——bmos 设备单字段 status；本设计三层正交 + 派生 allocatable。
> 4. **程序层缺失**——bmos 控制偏点位直连，无过程级程序封装（§13）。
>
> **此前版本误判"bmos 缺房间层"已修正**：bmos 实际有完整的房间模块（platform factory 子模块），且 MES 工序已支持绑房间，与本设计的房间定位高度一致——这是产品化多产线适配的**已具备的基础**，而非缺口。

## 12. 设备控制与采集接入（直连执行底座）

本设计在前 11 章建立的设备模型基础上，引入**设备控制**和**数据采集**两个正交维度。

> **本章定位**：本章描述的是**直连执行路径（DIRECT）的底座**——点位映射、协议驱动、采集配置。工艺**不直接使用**本章的点位命令；工艺面对的控制入口是 §13 的"设备程序层"，由程序执行器按设备的 `executeMode` 路由——DIRECT 模式才落到本章的点位层，BATCH 模式则下发到现场控制层。读者请将本章理解为 §13 的直连底座，而非控制的全部。

### 12.1 设计原则

1. **业务代码不碰点位地址**：所有控制意图以领域命令表达，点位地址作为设备级配置隔离在适配层。
2. **控制与采集分离**：控制是带业务语义的少量读写（启动、设参数、读关键状态），采集是高频时序数据（温度曲线、振动）。两者逻辑独立、通道独立，互不阻塞。
3. **协议可配置**：协议（OPC UA / MQTT / Modbus / …）是设备的配置维度，不是代码里的分支条件。新增协议不改业务、不改命令翻译层。
4. **直连为主、Batch 预留**：当前只做直接控制（MES ↔ 设备），但抽象层为将来"通过 Batch 系统控制"留口子，扩展时设备模型不变。

### 12.2 控制栈抽象

控制栈分三层，自上而下逐层解耦：

```
业务代码
  │  发领域命令（StartEquipment / SetParameter / ReadValue / …）
  ▼
命令执行器（Command Executor）
  │  职责：把领域命令翻译成点位操作序列
  │  依据：设备的 ControlProfile（点位映射表 + 完成策略）
  ▼
协议驱动（Driver）—— 可插拔
  ├─ OPC UA Driver
  ├─ MQTT Driver
  ├─ Modbus Driver
  └─ …（未来：Batch Driver）
  │
  ▼
设备 / 网关
```

各层职责边界：

| 层 | 知道什么 | 不知道什么 |
|---|---|---|
| 业务代码 | 设备 ID、领域命令 | 点位地址、协议、完成策略 |
| 命令执行器 | 命令→点位映射、完成策略、协议选择 | 协议具体怎么握手 |
| 协议驱动 | 协议细节、连接管理 | 业务语义、命令含义 |

### 12.3 三类原子操作

所有领域命令最终分解为三类点位原子操作：

| 原子操作 | 语义 | 用途 |
|---|---|---|
| **Write** | 向某点位写值 | 触发动作、下发参数 |
| **Read** | 从某点位读当前值 | 查询状态、确认结果 |
| **Subscribe** | 订阅点位变化或事件 | 接收完成事件、报警 |

领域命令 = 一个或多个原子操作的有序组合。例如"启动设备"= `Write(Motor.Start=true)` + 等待完成；"设置转速并启动"= `Write(Setpoint.Speed)` + `Write(Motor.Start)` + 等待。

### 12.4 点位映射表（命令翻译的依据）

每台设备登记一张**命令→点位**映射表，作为 ControlProfile 的核心内容：

| 命令 | 原子操作 | 目标点位 | 备注 |
|---|---|---|---|
| Start | Write | 控制位 A | 触发启动 |
| Stop | Write | 控制位 B | 触发停止 |
| SetSpeed | Write | 参数点 S | 下发转速 |
| ReadSpeed | Read | 状态点 P | 读当前转速 |
| OnSpeedReached | Subscribe | 事件点 E | 速度到达事件 |
| OnAlarm | Subscribe | 报警点集 | 报警订阅 |

映射表的**有效配置是设备级的**（每台设备最终用一张有效映射表），但其组织分两层：类型提供默认模板，实例做覆盖/增删，合并后得到该设备的有效映射（见 §12.10.1）。换型号只改类型默认模板，业务代码和命令执行器都不动。

### 12.5 写命令的完成策略（设备级配置）

写点位是"发出指令"，不等于"动作完成"。完成判定策略作为**设备级配置**（同一台设备所有命令共用一种策略）：

| 策略 | 判定方式 | 适用 |
|---|---|---|
| **写即完成** | 写下去即视为成功 | 不重要的开关量、纯触发型 |
| **回读确认** | 写后读指定状态点，符合预期即完成，超时失败 | 大多数控制设备 |
| **事件确认** | 写后等待指定事件到达即完成，超时失败 | 有事件机制的设备 |

完成策略把"同步的写"包装成"带确认的语义操作"，让上层不必关心设备是即时的还是延迟响应的。

### 12.6 控制与采集分离

两者是**正交**的两个维度，刻意不解耦到同一通道：

| 维度 | 控制 (Control) | 采集 (Acquisition) |
|---|---|---|
| 语义 | 业务意图（启动/设参数）| 观测记录（温度曲线）|
| 频率 | 低频、按需 | 高频、周期 |
| 数量 | 少量关键点位 | 大量点位 |
| 通道 | 独立，怕被采集流量阻塞 | 独立，怕被控制逻辑拖慢 |
| 配置 | ControlProfile | AcquisitionProfile |

物理上两者可能走同一协议（如都走 OPC UA），但**逻辑通道和配置分开**。

### 12.7 连接管理（设计要求）

直连意味着 MES 维护到设备的通信连接，设计上需满足：

- **连接复用**：每台设备/网关的连接复用，不每命令新建。
- **断线重连**：连接中断后自动重连；重连期间命令排队或快速失败，不能静默丢失。
- **连接级心跳**：与 §7.4 的"业务占用心跳"区分——后者是业务层防丢设备，本处是通信层探活。两者独立。

这些是设计约束，具体实现（连接池机制、重连退避策略）不在本文档范围。

### 12.8 协议可扩展性

协议作为 Driver 的实现策略，遵循统一接口契约（写/读/订阅）。新增协议 = 新增一个 Driver 实现，**不改命令执行器、不改业务代码**。

本设计明确把"通过 Batch 系统控制"作为未来协议的一种（Batch Driver）预留：

- 当前：仅直连类 Driver（OPC UA / MQTT / Modbus）。
- 未来：Batch Driver 实现"下发配方→订阅阶段事件"的语义，对命令执行器表现为另一种"协议"。
- 扩展代价：新增 Driver 实现 + 设备 ControlProfile 增加 Batch 配置段；设备模型本体、业务代码、命令翻译逻辑不变。

### 12.9 对设备模型的增量

设备台账（§5）新增两个维度：

```
Equipment
 ├─ ...（§5 原有内容）
 │
 ├─ controlMode: DIRECT | BATCH        ← 枚举，当前仅 DIRECT，BATCH 预留
 │
 ├─ ControlProfile                     ← 控制配置（直连核心）
 │   ├─ protocol: OPC_UA | MQTT | MODBUS | ...
 │   ├─ endpoint: 连接地址
 │   ├─ completionStrategy: WRITE_NOW | READBACK | EVENT
 │   ├─ commandMappings: 命令→点位 映射表
 │   └─ driverConfig: 驱动相关参数（超时、安全策略等）
 │
 └─ AcquisitionProfile                 ← 采集配置（与控制正交）
     ├─ points: 采集点列表（点位、周期、量纲）
     ├─ storageStrategy: 时序存储策略
     └─ alarmRules: 报警规则（阈值/事件）
```

### 12.10 配置的组织与管理

§12.9 给出了 ControlProfile / AcquisitionProfile 的字段，本节回答"配置如何配置"——组织单元、映射表形态、覆盖约束、生命周期。

#### 12.10.1 组织单元：类型默认 + 实例覆盖（两层）

配置结构**与能力模型（§4.2）同构**：类型层定义模板，实例层填差异。

```
设备类型 (EquipmentType.controlTemplate)
 ├─ protocol: OPC_UA                        ← 同型号统一协议
 ├─ addressScheme: 命名空间/前缀规则          ← 地址格式约定
 └─ defaultMappings: 命令→点位 模板（见 12.10.2）
        │ 同型号设备继承
        ▼
设备实例 (Equipment.controlProfile)         ← 只填差异
 ├─ endpoint: opc.tcp://192.168.1.10:4840    ← 每台不同
 ├─ addressPrefix: EQP-001                   ← 代入模板的 {prefix}
 ├─ credentialRef: CR-2026-001               ← 凭据引用，不存明文（见 12.10.4）
 ├─ completionStrategy: READBACK             ← 设备级完成策略（§12.5）
 ├─ mappingOverrides:                        ← 实例增删（改装场景）
 │   ├─ add:    [命令→点位]
 │   └─ remove: [命令名]
 ├─ driverConfig: 超时/重连/安全策略
 └─ effectiveMappings = type.defaultMappings ∪ add − remove

有效配置 = 类型默认 ∪ 实例新增 − 实例移除 ∪ 实例覆盖项
```

**两层同构的好处**：学过能力模型（§4.2）就懂配置模型，认知成本为零；同型号 100 台设备只填 endpoint+凭据；厂商固件升级改点位地址，改类型一处、全批生效，且实例的改装增删不被抹掉。

#### 12.10.2 点位映射表形态：分组表

映射表采用**分组表**（而非扁平表或声明式），按功能分组组织命令→点位：

| 分组 | 含义 | 操作类型 | 示例 |
|---|---|---|---|
| `control` | 控制位（触发型）| Write | Start / Stop / Reset |
| `parameter` | 参数（带值 Write）| Write | SetSpeed / SetTemp |
| `status` | 状态读数 | Read | ReadSpeed / ReadTemp |
| `event` | 事件订阅 | Subscribe | OnSpeedReached |
| `alarm` | 报警订阅 | Subscribe | OnAlarm |

分组表示例（实例有效映射）：

```
[control]
  Start   | Write | ns=2;s=EQP-001.Motor.Start
  Stop    | Write | ns=2;s=EQP-001.Motor.Stop
  Reset   | Write | ns=2;s=EQP-001.Motor.Reset

[parameter]
  SetSpeed | Write | ns=2;s=EQP-001.Setpoint.Speed
  SetTemp  | Write | ns=2;s=EQP-001.Setpoint.Temp

[status]
  ReadSpeed | Read | ns=2;s=EQP-001.Actual.Speed
  ReadTemp  | Read | ns=2;s=EQP-001.Actual.Temp

[event]
  OnSpeedReached | Subscribe | ns=2;s=EQP-001.Event.SpeedReached

[alarm]
  OnAlarm | Subscribe | ns=2;s=EQP-001.Alarm.*
```

**选分组表的理由**：比扁平表有结构（适配中等复杂度设备），比声明式简单（无需命令推导引擎）。分组天然对应 §12.6 的控制/采集分离，也对应操作员看板的视觉分组（控制按钮一组、状态读数一组）。

> 未来若设备点位标准化程度提高、需跨厂商互操作，可演进到声明式（点位+元数据，命令由推导规则组装）。分组表能相对平滑地迁移。

#### 12.10.3 覆盖约束（实例能改什么、不能改什么）

| 配置项 | 实例可覆盖？ | 说明 |
|---|---|---|
| `protocol` | ❌ 不可覆盖 | 同型号设备协议应统一；换协议应建新类型。守住类型契约。|
| `endpoint` | ✅ | 每台设备地址不同 |
| `addressPrefix` | ✅ | 同型号不同 PLC 的 namespace 差异 |
| `credentialRef` | ✅ | 每台设备凭据独立 |
| `completionStrategy` | ✅ | 设备级（§12.5）|
| `commandMappings` | ✅ 增/删 | 改装、加装、点位停用 |
| `driverConfig` | ✅ | 超时/重连等运行参数 |

**关键约束：协议不可在实例覆盖。** 理由：类型 = 协议 + 默认映射模板，是稳定契约；若允许实例改协议，同型号设备的命令映射语义会破裂（OPC UA 地址和 Modbus 寄存器无法共用一张模板）。换协议的正确做法是新建类型。

#### 12.10.4 安全凭据

endpoint 之外的证书、密钥、账号密码**不存明文**：

- 配置表只存 `credentialRef`（凭据引用 ID）。
- 运行时由协议驱动凭引用 ID 从凭据保险柜取凭据。
- 复用平台既有的加密/凭据管理基础设施。

#### 12.10.5 地址格式：协议相关原始串

不同协议的地址形态差异大（OPC UA 的 `ns=2;s=...`、MQTT 的 topic、Modbus 的寄存器号），映射表的"点位地址"列**存协议相关的原始字符串**，由对应协议驱动自行解析。

- **不**做协议无关的统一地址抽象——首版复杂度过高，且单台设备协议不频繁换。
- 换协议时（走新建类型路径）地址自然重配，无迁移负担。

#### 12.10.6 配置生命周期

| 关注点 | 设计要求 |
|---|---|
| 配置者 | 调试/实施工程师配点位；工艺工程师不介入 |
| 生效方式 | 改 endpoint/凭据需重连；改映射表可热生效（不重连）|
| 版本管理 | 配置带版本，支持回滚 |
| 保存校验 | 至少语法校验（地址格式、必填项）；可选连通性测试（ping endpoint）|
| 影响分析 | 改类型默认映射时，需提示受影响的实例清单 |

#### 12.10.7 采集配置的同构

AcquisitionProfile 采用**与 ControlProfile 相同的两层结构**（类型默认采集点 + 实例增删）和分组逻辑（采集点按 `status`/`event`/`alarm` 归组，与控制共享分组语义）。本节不重复展开，结构同 §12.10.1–12.10.3。

### 12.11 控制接入的设计取舍

| 取舍点 | 选择 | 放弃了什么 | 何时需要重新考虑 |
|---|---|---|---|
| 抽象层 | 命令执行器 + 协议驱动 | 直连性能的极致优化 | 当命令延迟成为瓶颈、抽象开销不可忽略时 |
| 协议维度 | 设备级可配置 | 单协议硬编码的简单 | 当现场协议稳定不变、且需极致轻量时 |
| 完成策略 | 设备级单一策略 | 命令级差异化策略 | 当同一设备不同命令确实需要不同完成判定时 |
| 控制/采集 | 正交分离 | 统一通道的简单 | 当采集和控制量都很小、分离收益不显时 |
| 直连/Batch | 直连为主、Batch 预留 | 首版即支持 Batch 的完整能力 | 当短期内确实要接入 Batch 系统时 |
| 配置组织 | 两层（类型默认+实例覆盖），与能力模型同构 | 实例自包含的简单 | 永不——同构降低认知成本，厂商固件升级需类型层一处生效 |
| 协议可覆盖性 | 实例不可改协议 | 实例完全自由 | 当同型号设备确需混用多协议时（建议拆类型而非放开约束）|
| 映射表形态 | 分组表（control/parameter/status/event/alarm）| 扁平表的简单 / 声明式的灵活 | 当点位标准化、需跨厂商互操作时，演进到声明式 |

## 13. 设备程序层（Batch 抽象）

### 13.1 为什么需要这一层

§12 的"命令→点位"是**开关级**抽象。但真实设备操作往往是**过程级**的——"升温到 80 度"不是一次点位写，而是：打开加热 → PID 升温控制 → 持续监控温度 → 到位判断 → 结束。这是一段**有状态、有异常处理、需持续监控**的程序。

把这种过程直接写在工艺里会带来三类问题：

1. **重复**：每个用到升温的工序都要重配一遍，且工艺工程师被迫懂底层点位细节。
2. **不可调试**：过程散在工艺配置里，无法独立试运行、无法独立排查。
3. **GMP 风险**：持续监控、断电恢复、步骤审计等控制系统的工程责任，散落在 MES 业务层无法合规。

设备程序层（Batch 抽象）把"设备级操作过程"封装为可复用、可独立调试、可审计的**程序**，工艺只调用不实现；同时把监控/断电恢复/审计的工程责任收敛到专门的一层。该层对应 ISA-88 批控制思想。

### 13.2 定位与边界

- **上对工艺**：统一接口 `ExecuteProgram(programName, params)`——只声明执行什么程序及参数，不暴露点位、不暴露现场控制层细节。
- **下对设备**：按设备的 `executeMode` 路由到两条执行路径（DIRECT / BATCH）。
- **与 §12 的关系**：§12 降级为本层 DIRECT 路径的底座；本章是工艺唯一面对的控制入口。

### 13.3 三个分离（核心抽象）

| 层 | 设备无关？ | 内容 | 例子 |
|---|---|---|---|
| **程序库 Program Library** | ✅ 平台共享 | 程序的逻辑步骤定义 | Heating = 设定目标温度 + 等待到位 + 判断完成 |
| **程序绑定 Program Binding**（挂类型/设备）| ❌ 设备相关 | "这台设备如何执行某程序" | 设备 X 的 Heating → 下发 DCS 配方；设备 Y 的 Heating → 展开成点位序列 |
| **程序调用**（工艺侧）| ✅ | 只声明程序名 + 参数 | `ExecuteProgram("Heating", targetTemp=80)` |

> **为何程序库共享**：程序逻辑（升温=设定+等待+判断）对所有设备都一样，重复存无意义；改逻辑时一处生效。与能力模型（§4.2）、控制配置（§12.10）的"类型默认+实例覆盖"**同构**。

### 13.4 执行路径（统一抽象）

```
工艺 ──ExecuteProgram(prog, params)──► 程序执行器
                                          │
                                          │ 查设备 executeMode + programBinding
                                          │
                    ┌─────────────────────┴─────────────────────┐
                    ▼                                           ▼
            executeMode=DIRECT                          executeMode=BATCH
            （裸点位设备）                                （自带控制层设备）
                    │                                           │
            按 §12 点位映射                                下发配方到现场控制层
            展开成点位操作序列                            订阅阶段完成事件
            （MES 程序执行器自己执行）                     （现场控制层自己执行）
                    │                                           │
                    └─────────────────────┬─────────────────────┘
                                          ▼
                              统一程序事件流（§13.5）
                                          │
                                          ▼
                                        工艺
```

**统一抽象的关键**：无论走哪条路径，对上都产出**同一套程序事件**（见 §13.5）。工艺只消费事件，不感知底层路径差异。

### 13.5 程序事件流（先粗后细）

程序执行器对工艺暴露统一的事件流。首版采用粗粒度四事件：

| 事件 | 含义 |
|---|---|
| `Started` | 程序已启动 |
| `Progress` | 执行中进展（含可选的阶段/进度信息）|
| `Completed` | 程序正常完成（含结果数据）|
| `Aborted` | 程序异常终止（含原因）|

> 首版粗粒度即可满足工艺编排。未来按需细化（如 `StepCompleted` / `ParameterApplied` / `PhaseReached`），细化时保持事件只增不改，向后兼容。

### 13.6 设备模型增量

设备/类型新增两个字段组：

```
Equipment（及 EquipmentType）
 ├─ executeMode: DIRECT | BATCH                 ← 决定走哪条执行路径
 └─ programBindings[]                           ← 程序绑定清单（类型默认 + 实例覆盖）
     ├─ programName: "Heating"                  ← 绑定到程序库的哪个程序
     ├─ impl: DCS_RECIPE | POINT_SEQUENCE       ← 实现方式
     ├─ recipeRef: REC-HEAT-001                 ← BATCH 模式：现场控制层的配方/程序 ID
     └─ pointSequence: [...]                    ← DIRECT 模式：点位操作序列（引用 §12 的映射）
```

> 程序绑定走"类型默认 + 实例覆盖"（同 §12.10.1、§4.2）：同型号设备的程序绑定模板由类型带出，实例只填差异（如具体配方 ID、改装后的点位调整）。

### 13.7 监控、断电恢复、GMP 的责任归属

§13.1 的三类工程责任在此明确归位：

| 责任 | DIRECT 路径 | BATCH 路径 |
|---|---|---|
| 持续监控 | MES 程序执行器（订阅点位、判断到位、超时处置）| 现场控制层自管，MES 收事件 |
| 断电恢复 | MES 持久化程序实例状态，重启后续跑或回滚 | 现场控制层保持，MES 重连后同步状态 |
| GMP 审计 | 程序执行器落**程序级**审计（程序、参数、起止、结果、操作人）| 现场控制层记录 + MES 接收归档 |

> BATCH 路径在这三件事上天然占优（现场控制层兜底）；DIRECT 路径则需 MES 程序执行器自行实现。这是混合架构下两种路径的固有差异，由程序执行器统一收敛对工艺透明。

### 13.8 与能力模型的关系

程序库是能力标签的**展开**：

| 维度 | 粒度 | 用途 |
|---|---|---|
| 能力 (Capability, §4) | 粗粒度布尔（可升温）| **匹配**——工艺选设备 |
| 程序 (Program, §13) | 过程级逻辑（升温怎么做）| **执行**——工艺调程序 |

设备同时持有两者：能力（匹配用）+ 程序绑定（执行用）。两者**关联但不强制等同**——有"可升温"能力的设备通常绑定 `Heating` 程序，但程序绑定是独立的配置项。

### 13.9 设计取舍

| 取舍点 | 选择 | 放弃了什么 | 何时重新考虑 |
|---|---|---|---|
| 抽象层 | 程序层 + 执行器统一路由 | 工艺直连点位的简单 | 永不——程序封装是 GMP/复用/调试的必需 |
| 程序逻辑归属 | 程序库平台共享 | 每设备自存完整程序 | 永不——同构于已定的能力/配置模型 |
| 混合架构呈现 | 统一抽象（executeMode 路由）| 直连/Batch 两套并行机制 | 永不——统一是工艺无感的前提 |
| DIRECT 路径 | 保留，作为 BATCH 的执行底座（§12）| 全部走 BATCH | 当现场全部设备都具备控制层时 |
| 事件粒度 | 粗粒度四事件 | 细粒度事件的精确 | 当工艺编排确需阶段级反馈时，按只增不改细化 |
| 程序绑定组织 | 类型默认 + 实例覆盖 | 实例自包含 | 永不——同构于 §4.2 / §12.10 |

## 14. 数据采集存储

§12.6 确立了"控制与采集分离"，§12.9 给出了 AcquisitionProfile 的字段骨架，但**采集数据存哪、怎么存、存多久、怎么查**此前未涉及。本章补齐采集存储的设计（不含具体选型，选型见 §15 开放问题）。

### 14.1 采集数据的本质：时序数据

采集数据（温度曲线、振动、电流）与业务数据（台账、工序、状态日志）是**两种不同的物种**，存储需求几乎相反：

| 维度 | 业务数据 | 采集数据 |
|---|---|---|
| 量级 | 每台设备几十~几百条 | 每台设备每秒~每分钟 N 个点位，海量 |
| 增长 | 业务事件驱动，慢 | 时间驱动，**持续高速写入** |
| 更新 | 频繁改（CRUD）| **几乎只写不改不删**（append-only）|
| 查询 | 按业务键查（设备ID、批次号）| **按时间范围 + 点位查** |
| 聚合 | 少 | **多**（avg/max/min/std/降采样）|
| 保留 | 长期（合规）| 分层（近期高频、远期降采样归档）|
| 价值密度 | 每条有业务意义 | 单条价值低，**趋势和异常才有价值** |

> **核心结论**：采集数据是时序数据，存储需求（高吞吐写入、时间范围查询、降采样聚合）与关系库擅长的事务/关联/CRUD 正好相反。塞进关系库一两个月就会遇写入瓶颈、查询超时、表膨胀。这就是工业界有专门时序数据库（TSDB）的原因。

### 14.2 三层存储模型

采集存储按**用途**分三层，每层职责、保留期、选型取向不同：

| 层 | 用途 | 保留期 | 选型取向 | 谁查 |
|---|---|---|---|---|
| **热数据** | 实时缓冲——监控、报警判定、运行态判定 | 秒~分钟，滚动覆盖 | 内存/缓存（不落库）| 报警规则、看板实时刷新、allocatable |
| **温数据** | 近期原始值——回放、工艺分析、故障排查、批记录数据回放 | 天~月（如 3–6 个月）| **时序库** | 工艺工程师、批记录生成、故障复盘 |
| **冷数据** | 远期归档——趋势分析、合规存档、历史对比 | 年~永久（GMP 常 5–10 年）| 降采样表 / 对象存储 | 长期趋势、审计抽查 |

**分层要点**：

- 热数据**不归"存储"管，归"运行时"管**——快进快出，丢得起（重启即失，下一秒又来）。若误把实时数据往库里塞，会拖垮写入。
- 冷数据**降采样**（downsampling）：把 1Hz 原始数据聚合成 1 分钟一条（min/max/avg），存储量降几个数量级，趋势分析够用。
- 三层之间有**数据流动**：热→温（定期落库）、温→冷（到期降采样归档）。

### 14.3 数据模型：tag + field + timestamp

时序数据的典型模型：

```
一条采集记录：
  timestamp:  2026-07-22T10:30:00.123Z
  tags:       equipmentId=EQP-001, pointId=PT-Temp-01, lineId=LINE-01,
              batchId=B-2026-001, stepInstanceId=S-42
  fields:     value=85.3, quality=GOOD
```

| 部分 | 作用 | 说明 |
|---|---|---|
| `timestamp` | 时间戳，主排序键 | 写入与查询的核心轴 |
| `tags` | 过滤/索引键 | equipmentId / pointId / lineId / batchId / stepInstanceId |
| `fields` | 实际数值 | value |
| `quality` | 数据质量 | GOOD / UNCERTAIN / BAD——采集自带，**不可丢** |

> `tags` 决定"能怎么查"：设计 tags 时要前瞻性考虑查询场景（按设备？按批次？按产线？），tags 定错=查不出来。

### 14.4 AcquisitionProfile 的扩展

§12.9 的 AcquisitionProfile 字段过简，本章扩展为：

```
AcquisitionProfile
 ├─ points[]                       ← 采集点清单（类型默认 + 实例覆盖，同 §12.10）
 │   ├─ pointId                    ← 点位标识（与控制层点位地址解耦）
 │   ├─ address                    ← 协议地址（引用 §12.10 的地址规则）
 │   ├─ unit                       ← 量纲（℃ / rpm / kg）
 │   ├─ period                     ← 采集周期（1s / 1min）→ 决定写入频率
 │   ├─ qualityRule                ← 数据质量判定规则（GOOD/UNCERTAIN/BAD）
 │   ├─ storageTier                ← 进热/温/冷哪几层
 │   ├─ retention                  ← 各层保留时长
 │   └─ downsamplePolicy           ← 降采样策略（冷层用）
 └─ alarmRules[]                   ← 报警规则（关联健康态，见 §14.6）
```

> 与 ControlProfile 同构：采集点清单也走"类型默认 + 实例覆盖"，改装/加装场景在实例层增删采集点。

### 14.5 采集数据与业务上下文的关联（GMP 关键）

采集数据不是孤立的，必须能反查到业务上下文，否则批记录和追溯不完整：

| 关联 tag | 用途 |
|---|---|
| `equipmentId` | 查"这台设备的温度曲线" |
| `lineId` / `roomId` | 按位置聚合查询 |
| `batchId` / `stepInstanceId` | 查"这批产品升温阶段的曲线"——批记录数据回放 |

**关键设计**：采集写入时，把**当前的 batchId / stepInstanceId 作为 tag 带上**。这样批记录能直接拉出"本批次相关的所有采集曲线"，GMP 追溯才完整。

> 这要求采集写入端知道"当前这台设备正被哪个批次/工序占用"——从 §7.2 的占用标志（occupant）取值。采集与占用标志有隐含的数据流：占用方是谁 → 写到采集 tag 里。

### 14.6 报警与状态的联动

采集数据 → 报警规则 → 触发健康态 `Alarm`（§7）。链路明确：

```
采集值（热数据）
   │
   ▼ 报警规则评估
   │
 超阈值？ ──是──► 写健康态 Alarm（§7.1 Health）
   │           └ 同时写报警事件（时间/值/阈值/设备，供追溯）
   │ 否
   ▼ 继续监测
```

报警规则分两层：

| 报警类型 | 数据源 | 响应 |
|---|---|---|
| 实时报警 | 热数据（秒级原始值）| 立即触发健康态 Alarm |
| 趋势报警 | 温数据（分钟级聚合后）| 渐变型异常（如温度缓慢爬升）|

> 报警规则挂在 AcquisitionProfile（设备级），但其效果（健康态变化）影响全局 allocatable（§7.3）。

### 14.7 查询模式（设计要求）

采集存储必须高效支撑以下查询，选型和索引设计要据此验证：

| 查询 | 模式 |
|---|---|
| 实时看板 | 某设备最近 N 秒的某点位值（热数据）|
| 曲线回放 | 某设备某时段多点位曲线（温数据）|
| 批记录数据回放 | 某批次某工序时段的所有采集曲线（温数据，按 batchId + 时间范围）|
| 故障复盘 | 故障时刻前后 N 分钟的高频数据（温数据）|
| 长期趋势 | 某设备过去一年的日均值（冷数据，降采样后）|
| 合规抽查 | 某时段原始数据导出（温数据，保留期内）|

### 14.8 设计取舍

| 取舍点 | 选择 | 放弃了什么 | 何时重新考虑 |
|---|---|---|---|
| 采集 vs 业务存储 | 分离（采集走时序存储）| 统一关系库的简单 | 永不——时序数据塞关系库必然翻车 |
| 存储分层 | 热/温/冷三层 | 单层存的简单 | 当数据量极小、三层开销不划算时 |
| 冷数据 | 降采样归档 | 全量原始永久存的存储成本 | 当合规要求必须永久保留原始粒度时 |
| 业务上下文 tag | 写入时带 batchId/stepInstanceId | 不带关联的纯时序 | 永不——不带则批记录无法回放，GMP 不达标 |
| 选型 | 暂不绑定（留开放问题）| 明确推荐栈 | 待现场调研数据量/保留期/现有基础设施后定（见 §15）|

## 15. 待确认 / 开放问题

以下问题在本文档中未最终定案，列出供后续讨论：

1. **能力的版本治理**：能力码发布后能否废弃？废弃后历史工艺如何匹配？（建议：能力只废弃不删除，历史工艺按需快照）
2. **房间层是否独立建表**：还是作为工位的一个属性？（建议：独立建表，房间有自己的属性如洁净级别、面积）
3. **规格参数不参与匹配的严格性**：是否允许极少数"参数硬约束"作为能力的补充（如某工序必须用 ≥ 50L 容器）？（建议：先严守"参数不匹配"，出现真实需求再开例外）
4. **设备挪位置的流程**：挪位置是否需要审批？是否影响在执行的工序？（建议：挪位置需审批，且仅允许在设备未占用、Health=Normal 时挪）
5. **多产线工艺的产线选择时机**：排程期自动选还是人工选？（建议：人工选为主，自动选为辅）
6. **占用中设备异常的处置**：占用中设备运行态变 Error 或健康态变 Alarm 时，是否自动解除占用？（§8.5 引用本条。建议：Error 不自动解除——可能自恢复；Alarm 自动解除并通知占用方）
7. **凭据保险柜的方案**：credentialRef 指向的凭据存储复用平台哪套基础设施？配置变更时凭据如何轮换？
8. **配置版本回滚粒度**：是整份 ControlProfile 回滚，还是单条映射回滚？回滚是否触发重连？
9. **同型号设备混用多协议**：当现场确有同型号设备分别走 OPC UA / Modbus 时，是拆成两个类型（当前约束），还是放开"协议不可实例覆盖"约束？（建议：先守约束拆类型，案例多了再评估）
10. **程序库的版本治理**：程序逻辑定义（如 Heating 的步骤）变更后，已下发的工艺如何处理？是否需要程序版本号 + 历史工艺快照？（与本节 #1 的能力版本治理同源）
11. **DIRECT 路径的断电恢复策略**：MES 程序执行器持久化程序实例状态后，重启后是续跑还是回滚？续跑的边界（已到哪一步可续）如何判定？
12. **程序绑定的可调试性**：程序绑定（尤其 DIRECT 的 pointSequence）如何独立于工艺试运行？是否提供"设备级程序调试"入口？
13. **现场控制层的对接协议**：BATCH 路径下发配方/接收事件，与现场 DCS/PLC 的具体对接协议（OPC UA 方法调用、专有 API、文件交换等）未定，待现场调研后补充。
14. **程序事件流的订阅模型**：工艺是主动轮询程序状态，还是订阅推送？推送失败的重传策略？
15. **采集存储选型**：温层数据选哪类时序库（专业 TSDB / 关系库时序扩展 / 对象存储），冷层是否复用 bmos 已有 MinIO？依赖现场数据量、保留期、现有基础设施调研。
16. **采集数据保留与降采样策略**：各层具体保留多久（合规要求的 5–10 年如何分配温/冷）？降采样粒度（1 分钟？10 分钟？）？哪些点位需永久原始保留（如关键工艺参数）？
17. **采集与占用的数据流**：采集写入时从占用标志取 batchId/stepInstanceId 写入 tag（§14.5），这个取值的时机和一致性如何保证（占用切换瞬间的采集归属）？
